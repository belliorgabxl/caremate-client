01

ภาพรวมสถาปัตยกรรม

ระบบมีผู้เล่น 3 ฝ่าย แอปนี้คุยกับ backend ตรง ๆ ไม่ผ่าน BFF อีกแล้ว และ ไม่มี push/webhook กลับมาหาแอป — ข้อจำกัดข้อนี้เป็นตัวกำหนดรูปร่างของ flow การจับคู่ทั้งหมด

ผู้เล่นในระบบ

client_appแอป Flutter ตัวนี้ — ฝั่งผู้ใช้/ญาติ
backendGo/Fiber — เจ้าของ business logic และ matching ทั้งหมด
partner appแอปผู้ดูแล — เป็นตัวที่ทำให้สถานะการจองเดินหน้า

กติกาที่ใช้ทั้งแอป

authcookie caremate_session ตัวเดียว ไม่มี bearer token
navใช้ context.go เสมอ ไม่ใช้ push/pop
stateRiverpod Provider<T> ธรรมดา โหลดใน initState
i18nUI copy เป็นภาษาไทยทั้งหมด ค่าใน field เป็นอังกฤษ
จุดที่ต้องจำ: หลัง POST /payments/confirm สำเร็จ backend จะยิง matching แบบ fire-and-forget แล้วจบ request ทันที แอปจึงต้อง poll เอง (GET /bookings/:id/mission) เพื่อจะรู้ว่าจับคู่ได้แล้วหรือยัง
02

แผนผังเส้นทางหน้าจอ

ทุกเส้นทางประกาศแบบ flat ใน app_routes.dart สี่เส้นทางกลางอยู่ใน ShellRoute เดียวกัน (แชร์แถบล่าง) ที่เหลือเป็นหน้าเต็มจอแยก

ก่อนเข้าสู่ระบบ

/splashตรวจ session แล้วเด้งออก
/loginเข้าสู่ระบบด้วยเบอร์โทร
/registerสมัคร + ประตู PDPA

แถบล่าง 4 แท็บ (ShellRoute)

/homeหน้าแรก
/bookingจองบริการ (wizard 5 ขั้น)
/membersสมาชิกที่ดูแล
/profileโปรไฟล์

หน้าเต็มจอแยก

/paymentชำระเงิน PromptPay
/booking/status/:bookingIdติดตามสถานะ + polling
/booking/historyประวัติการจอง

กลุ่มโปรไฟล์

/profile/personal-informationข้อมูลส่วนตัว
/profile/health-informationข้อมูลสุขภาพ
/profile/addressesที่อยู่ของฉัน
/profile/settingsตั้งค่าความปลอดภัย

ทิศทางของ transition

เนื่องจากแอปไม่ใช้ navigation stack จริง (ไม่มี push/pop) router จึงใช้สัญญาณ navDirection บอกทิศเอง — goForward เลื่อนเข้าจากขวา (300 ms), goBack เลื่อนเข้าจากซ้าย (260 ms) รวมถึงการสลับแท็บล่างด้วย (MainScaffold เทียบ index ของแท็บที่กดกับแท็บปัจจุบันก่อนเรียก go)

03

เปิดแอป & ประตูตรวจสิทธิ์

AuthController มีสามสถานะ และ redirect ของ go_router อ่านสถานะนี้ทุกครั้งที่เปลี่ยนหน้า ทำให้ไม่มีทางหลุดเข้าหน้าที่ต้อง login ได้

1
Splash /splash

ยิง checkSession() ทันทีใน initState ระหว่างนั้นแสดงโลโก้ + spinner — restoreSession() อ่าน cookie ที่เก็บไว้ ถ้าไม่มีเลยก็จบที่ loggedOut ทันที ถ้ามีจะเอาไป re-validate กับ backend

LOCALreadSessionCookie() GET/authentication/me
2
ตัดสินใจตามสถานะ
  • checking — บังคับอยู่ที่ /splash เท่านั้น
  • loggedOut — อนุญาตเฉพาะ /login กับ /register นอกนั้นเด้งไป /login
  • authenticated — ถ้าอยู่ที่ splash/login/register จะเด้งไป /home

ถ้า /authentication/me ตอบ 401 จะล้าง session ทิ้งแล้วถือว่า loggedOut (error อื่นไม่ล้าง cookie)

3
เข้าสู่ระบบ /login

กรอก เบอร์โทรอย่างเดียว — ไม่มีรหัสผ่าน ไม่มี OTP ในเวอร์ชันนี้ backend ตอบกลับพร้อม Set-Cookie แอปดึง cookie ออกจาก response header เก็บลง LocalStorage แล้ว interceptor ของ Dio จะแนบให้ทุก request ถัดไปเอง

POST/authentication/login GET/authentication/me
04

สมัครสมาชิก + ประตูยินยอม PDPA

จุดที่คนเข้าใจผิดบ่อย: PDPA ไม่ใช่หน้าแยกและไม่ใช่ route — มันเป็น modal เต็มจอ ที่แทรกกลางฟังก์ชัน _register() หลังฟอร์มผ่าน validate แล้ว แต่ก่อนยิง API สร้างบัญชี

1
กรอกฟอร์ม /register

แอปบังคับกรอกครบทุกช่อง: ชื่อจริง · นามสกุล · ชื่อเล่น · เพศ · วันเกิด · อีเมล · เบอร์โทร ทั้งที่ backend บังคับแค่ 3 ช่องแรก — เป็น นโยบายฝั่ง frontend ที่ตั้งใจให้เข้มกว่า ส่วนที่อยู่ / ข้อมูลสุขภาพ / ผู้ติดต่อฉุกเฉิน ยกไปกรอกทีหลังในหน้าโปรไฟล์

  • เพศส่งเป็นค่าอังกฤษ male/female/other แสดงผลไทย
  • วันเกิดส่งเป็น YYYY-MM-DD
2
ดึงนโยบายฉบับปัจจุบัน

GET /pdpa เป็น public ไม่ต้อง auth ตัว content ที่ได้เป็น HTML สำเร็จรูป เลย render ด้วย widget Html ตรง ๆ ไม่ต้อง parse markdown ถ้าเรียกไม่สำเร็จ (เน็ตหลุด หรือ 404 เพราะยังไม่มีเวอร์ชัน active) จะตกไปใช้ ฉบับที่ฝังมากับแอป bundled-2026-08-04 — การสมัครไม่มีวันถูกบล็อกเพราะ API นี้

GET/pdpa
3
ประตูเลื่อนอ่านจนจบ

ปุ่มยอมรับและ checkbox จะ ยังกดไม่ได้ จนกว่า ScrollController จะตรวจว่าผู้ใช้เลื่อนอ่านถึงท้ายเอกสารจริง ๆ ถ้ากดปิด (X) หรือไม่เคยเลื่อนถึงท้าย จะได้ค่า null กลับมาและ ยกเลิกการสมัครก่อนยิง API ใด ๆ

4
บันทึกความยินยอม แล้วจึงสร้างบัญชี

บันทึกลงเครื่องก่อน (timestamp UTC + เลขเวอร์ชันที่ผู้ใช้เห็นจริง) แล้วค่อยยิงสมัคร โดยแนบ pdpaConsent / pdpaConsentVersion ไปด้วย

LOCALsavePdpaConsentGiven(version) POST/authentication/register GET/authentication/me
ข้อจำกัดที่ยังเปิดอยู่: RegisterRequest ฝั่ง Go ยังไม่มี field รับ consent — ตอนนี้สองฟิลด์นั้นถือว่าถูก backend มองข้ามไปเฉย ๆ และยังไม่มี endpoint ให้อ่านสถานะ consent กลับมาแสดงในหน้าโปรไฟล์
05

หน้าแรก

ทำหน้าที่เป็นแผงสรุป + ทางลัด โหลดสองอย่างเรียงกันตอนเข้าหน้า

1
โหลดข้อมูล /home

ดึงรายชื่อสมาชิกก่อน แล้วดึงรายการจองที่ยัง active (กรอง COMPLETED/CANCELLED/PAYMENT_EXPIRED ออกฝั่งแอป) รองรับดึงลงเพื่อ refresh และถ้าโหลดพังจะขึ้น empty state พร้อมปุ่มลองใหม่

GET/user-relatives GET/bookings
2
สิ่งที่แสดง
  • ทักทายด้วยชื่อผู้ใช้จาก AuthController.user
  • ตัวเลขสรุป 3 ช่อง — จำนวนสมาชิก · นัดหมาย · รายการรอชำระ
  • การ์ดนัดหมายล่าสุด พร้อมป้ายสถานะและปุ่มลัดไปหน้าติดตาม
  • ถ้ามีรายการ AWAITING_PAYMENT จะโชว์ทางลัดไป /payment
06

สมาชิกที่ดูแล

การจองทุกครั้งต้องระบุว่าจองให้ใคร หน้านี้จึงเป็น เงื่อนไขบังคับก่อนจองได้ เพดานอยู่ที่ 5 คน (ไม่นับตัวเอง)

1
รายการ + ตัวกรอง /members

ค้นหาด้วยชื่อ/ความสัมพันธ์/เบอร์โทร และกรองด้วยชิป ทั้งหมด · ตัวเอง · ครอบครัว · ค่าเริ่มต้น รายการที่ isActive == false ถูกกรองทิ้งตั้งแต่ชั้น repository

GET/user-relatives
2
เพิ่มสมาชิก — สองจังหวะ ไม่ใช่จังหวะเดียว

เช็กเพดาน 5 คนฝั่งแอปก่อน แล้ว POST สร้าง จากนั้น ต้องยิง PATCH ตามทันที เพราะ CreateUserRelativeRequest ของ backend ไม่มีช่อง nickname/bloodType เลย และ dateOfBirth ที่ส่งไปกับ POST ก็ไม่ถูกบันทึกจริง (บั๊กฝั่ง repo) ถ้าไม่ PATCH ตาม ค่าพวกนี้จะเป็น NULL

  • ชื่อ–นามสกุลเป็น สองช่องแยก ส่ง firstName/lastName ตรง ๆ ไม่ตัดคำเดา
  • อายุถูกแปลงเป็นวันเกิดโดยประมาณ (ปีปัจจุบัน − อายุ) ก่อนส่ง
POST/user-relatives PATCH/user-relatives/:id
3
แก้ไข · ตั้งเป็นค่าเริ่มต้น · ลบ

แก้ไขใช้ PATCH ครั้งเดียวจบ ส่วน "ตั้งเป็นค่าเริ่มต้น" ต้อง GET ข้อมูลเดิมมาก่อนแล้วส่งกลับไปทั้งก้อนพร้อม isDefault: true เพราะ endpoint เป็นการเขียนทับ ไม่ใช่ patch บางส่วน

PATCH/user-relatives/:id GET/user-relatives/:id DELETE/user-relatives/:id
ยังใช้ไม่ได้: backend ยังไม่มี route DELETE /user-relatives/:id ปุ่มลบจึงได้ 404 กลับมาจนกว่าฝั่งนั้นจะเพิ่มให้
07

จองบริการ — wizard 5 ขั้น

เป็น PageView ที่ปิด swipe (NeverScrollableScrollPhysics) บังคับให้เดินผ่านปุ่มเท่านั้น เพื่อให้ด่านตรวจแต่ละขั้นทำงานได้จริง

ด่านแรกสุด: ถ้าบัญชียังไม่มีสมาชิกเลย หน้านี้จะถูกแทนที่ด้วยหน้า "ยังไม่มีผู้รับบริการ" ทั้งหน้า พร้อมปุ่มไปเพิ่มสมาชิก — ไม่ปล่อยให้กรอกไปสามขั้นแล้วค่อยไปตันที่ขั้นเลือกคน

ขั้นตอนและด่านตรวจ

1
เลือกบริการ

โหลดจาก GET /care/services เอาเฉพาะที่ is_active บริการที่ slug == 'transport' เท่านั้นที่จะบังคับให้กรอกปลายทางในขั้นที่ 4 (เช็ก slug ตรงตัว ไม่ใช่เดาจากชื่อ)

GET/care/services GET/user-relatives GET/payments/methods
2
เลือกวันและช่วงเวลา
  • วันที่เลือกได้ตั้งแต่วันนี้ถึง +60 วัน
  • เวลาเป็น ช่วงอิสระ — เลือกชิปสำเร็จรูป หรือกำหนดเองด้วย time picker ทั้งต้นและปลาย
  • ถ้าเวลาสิ้นสุดไม่มากกว่าเวลาเริ่ม ระบบถือว่า duration = 0 และไม่ให้ยืนยัน
3
เลือกผู้รับบริการ

เลือกจากรายการสมาชิก ถ้าเป็นตัวเองจะส่ง isForSelf: true และ relativeId: null ถ้าไม่ใช่ต้องส่ง relativeId เสมอ (backend บังคับ)

4
เลือกสถานที่

ใช้ LocationPickerPage ตัวเดียวกับหน้าที่อยู่ในโปรไฟล์ (มีช่องค้นหา geocoding ในตัว ไม่ต้องใช้ API key) ค่าเริ่มต้นของจุดรับคือที่อยู่ของสมาชิกคนแรก

  • ด่าน: จุดรับ ต้องมีพิกัดจริง ไม่ใช่แค่ข้อความ
  • ด่าน: ถ้าเป็นบริการ transport ปลายทางต้องมีพิกัดด้วย
  • ระยะทางคำนวณฝั่งแอปด้วยสูตร haversine เพื่อโชว์ประมาณการ
5
สรุปและยืนยัน

ก่อนยิงจริงจะตรวจซ้ำทั้งหมดอีกรอบ (พิกัดจุดรับ · ปลายทางถ้าจำเป็น · ช่วงเวลา · ต้องหา paymentMethodId ของ PromptPay เจอ) เมื่อสำเร็จจะเด้งไปหน้าชำระเงินทันที

POST/bookings/create

การคิดราคา

ตัวเลขที่โชว์ในแอปคำนวณเองเพื่อให้เห็นก่อนกดยืนยัน — ปัดเวลาขึ้นเป็นขั้นละ 30 นาที แล้วคิดตามเรตต่อชั่วโมงของบริการ บวกค่าแพลตฟอร์มคงที่

ส่วนประกอบที่มาสูตร
เวลาที่คิดเงินbillingStepMinutes = 30ปัดขึ้นทีละ 30 นาที
ค่าบริการservice.base_feebase_fee × (นาทีที่คิดเงิน ÷ 60)
ค่าแพลตฟอร์มplatformFee = 20.0คงที่ (ฝั่งแอป)
ระวังสองเรื่อง: (1) เวลาที่ส่งขึ้น backend ต้องเป็น RFC3339 พร้อม offset — toIso8601String() ของ Dart ไม่ใส่ timezone ให้ ทำให้ Go ปฏิเสธ จึงมี helper _toRfc3339() ไว้เฉพาะ · (2) paymentMethodId ต้องเป็น UUID จริง จาก GET /payments/methods ไม่ใช่ slug — slug จริงของ PromptPay คือ qr_promptpay

ราคาสุดท้ายที่มีผลคือตัวที่ backend ตอบกลับใน response ของ POST /bookings/create (totalAmount, platformFee, partnerPayout, distanceKm) ตัวเลขในแอปเป็นการประมาณการก่อนยืนยันเท่านั้น

08

ชำระเงิน

จองเสร็จ booking จะอยู่ที่ AWAITING_PAYMENT และมีนาฬิกา 15 นาทีเดินอยู่ฝั่ง backend (Redis TTL)

1
หารายการที่รอชำระ /payment

ถ้าเพิ่งจองในรอบนี้ จะใช้ข้อมูลที่ค้างไว้ในหน่วยความจำของ repository เลย (เพราะมีชื่อบริการ/ไอคอน/ชื่อผู้รับบริการครบ ซึ่ง endpoint รายการไม่ส่งกลับมา) ถ้าเปิดแอปใหม่แล้วค่อยมาจ่าย จะไปถาม /users/payment-check แทน

GET/users/payment-check GET/payments/methods GET/payments/:paymentId
2
แสดง QR PromptPay

QR ถูกสร้างในเครื่อง ด้วยอัลกอริทึม EMVCo + CRC16 ไม่มี endpoint ฝั่ง backend (ยกมาจาก proxy Next.js เดิม) จะสร้างก็ต่อเมื่อวิธีชำระที่เลือกมี slug เป็น qr_promptpay เท่านั้น

  • นับถอยหลังจาก payment.expiredAt ทุกวินาที
  • ปุ่มยืนยัน ล็อกไว้ 5 วินาทีแรก กันกดก่อนสแกน

ยืนยันการชำระ

การยกเลิกการจอง

ฝั่ง backend ทำทั้งหมดใน transaction เดียว ล็อกแถวด้วย FOR UPDATE ตามลำดับ bookings → payments เพื่อไม่ให้ deadlock กับ confirm/expire payment ฝั่งแอปมีทางเข้าสองที่

ทางเข้าหลัก

/booking/status/:idหน้ารายละเอียดการจอง — หน้าเดียวกับที่กดเข้าจากการ์ดนัดหมายในหน้าแรกและจากประวัติ ใช้ได้ทั้งสามสถานะที่ยกเลิกได้

ทางลัดตอนยังไม่จ่าย

/paymentลิงก์ "ยกเลิกรายการจองนี้" ใต้การ์ด QR — คนที่เปลี่ยนใจตอนเห็นยอดจะได้ไม่ต้องออกไปหารายการเองแล้วปล่อยให้ countdown เดินต่อ

ยกเลิกได้ตอนไหนบ้าง

AWAITING_PAYMENT ยกเลิกได้ — ยังไม่จ่าย ไม่มีเรื่องคืนเงิน
PENDING ยกเลิกได้ — หยุดการค้นหาผู้ดูแล จ่ายไปแล้วจึงต้องคืนเงิน
MATCHED ยกเลิกได้ — ผู้ดูแลจะได้รับ noti แจ้งยกเลิก และต้องคืนเงิน
IN_PROGRESS ยกเลิกเองไม่ได้ — mission เริ่มแล้ว มีผู้ดูแลออกงานจริง ต้องผ่านเจ้าหน้าที่ (ตอบ 409)
COMPLETED ยกเลิกไม่ได้ — จบงานแล้ว (ตอบ 409)
PAYMENT_EXPIRED ยกเลิกไม่ได้ — ตายไปเองแล้ว (ตอบ 409)

ลำดับการทำงาน

1
กดปุ่ม "ยกเลิกการจอง"

ปุ่มจะโผล่ก็ต่อเมื่อสถานะปัจจุบันยกเลิกได้จริง — เงื่อนไขฝั่งแอปสะท้อน IsBookingCancellableByUser ของ backend ตรง ๆ ไม่ต้องรอให้ยิงไปโดน 409 ก่อน

2
ยืนยันในกล่องโต้ตอบ

ข้อความอธิบายผลลัพธ์เปลี่ยนตามสถานะปัจจุบัน (ยังไม่จ่าย / กำลังหาคน / ได้คนแล้ว) พร้อมช่องกรอกเหตุผลแบบ ไม่บังคับ จำกัด 500 ตัวอักษร — ถ้าเว้นว่างจะไม่ส่ง key reason ขึ้นไปเลย

3
ยิง API

endpoint นี้ idempotent — กดซ้ำได้ อย่างมากก็ได้ 409 กลับมา ระหว่างรอผลปุ่มจะถูก disable และเปลี่ยนข้อความเป็น "กำลังยกเลิก..."

POST/bookings/:bookingId/cancel
4
สำเร็จ → หยุด poll แล้วเปลี่ยนหน้าจอ
  • ยกเลิก timer ทันที ไม่ต้องรอรอบถัดไป — หน้ารายละเอียดหยุด polling ส่วนหน้าชำระเงินหยุดทั้ง countdown และ timer ปลดล็อกปุ่ม แล้วพากลับหน้าแรก
  • เคลียร์รายการรอชำระที่ค้างในหน่วยความจำ ถ้าเป็นตัวเดียวกัน — กัน countdown ที่หน้าชำระเงินเดินต่อ (ฝั่ง server ลบ Redis expiry key ให้แล้ว)
  • แสดงสรุปการยกเลิก + เหตุผล และแถบเตือนคืนเงินถ้า refundRequired

สิ่งที่ backend ทำให้ในหนึ่ง transaction

  1. ตรวจว่าเป็น booking ของผู้ใช้คนนั้นจริง และสถานะยกเลิกได้
  2. payment ที่ยัง PENDING → CANCELLED — จำเป็น เพราะ sweeper กวาดเฉพาะ booking ที่ยัง AWAITING_PAYMENT ถ้าไม่ปิดจะค้าง PENDING ตลอดไป · ถ้า PAID อยู่แล้วปล่อยไว้แล้วตอบ refundRequired: true
  3. job offer ที่ยัง pending → expired กันพาร์ทเนอร์กดรับงานที่ยกเลิกไปแล้ว
  4. booking → CANCELLED พร้อม audit trail (cancelled_at, cancelled_by_type, cancelled_by_id, cancelled_reason)

นอก transaction แบบ best-effort: ลบ Redis key payment-expire · ส่ง noti booking_cancelled หาพาร์ทเนอร์ที่ถูก match แล้ว · เขียน audit log
