เปิดแอป & ด่านตรวจสิทธิ์

/splash

หน้าแรกสุดที่ผู้ใช้เห็นเสมอ ไม่ว่าจะเคยล็อกอินไว้หรือไม่ — เป็นหน้าที่ "รอผลตรวจ" ล้วน ๆ ไม่มีปุ่มให้กด

  • 1แอปเปิด SplashPage แล้วยิง checkSession() ทันทีใน initState
  • 2ตัวควบคุมอ่าน cookie caremate_session จาก LocalStorage แล้วลองเรียกโปรไฟล์
  • 3สำเร็จ → เด้งไป /home · ล้มเหลว/ไม่มี cookie → เด้งไป /login
Auth = cookie ตัวเดียว ระบบนี้ ไม่มี bearer token — login/register ตอบกลับพร้อม Set-Cookie: caremate_session แล้ว interceptor ของ ApiClient แนบกลับไปเองทุก request

เข้าสู่ระบบด้วยเบอร์โทร

/login

กรอกเบอร์โทร 10 หลักแล้วกดเข้าสู่ระบบได้เลย เนื่องจากยังไม่มีระบบ OTP

  • 1กรอกเบอร์ — เบอร์โทรที่ใช้สมัคร
  • 2กดปุ่ม → ปุ่มเปลี่ยนเป็น "กำลังเข้าสู่ระบบ..." พร้อมสปินเนอร์ กดซ้ำไม่ได้
  • 3สำเร็จ → router เด้งเข้า /home เอง ไม่ต้องสั่ง navigate
  • 4ล้มเหลว → ข้อความแดงใต้ปุ่ม (ข้อความจาก API หรือ "เข้าสู่ระบบไม่สำเร็จ กรุณาลองใหม่อีกครั้ง")
02

สมัครสมาชิก แล้วผ่านด่านยินยอม PDPA

/registerPdpaConsentDialog (modal)

ลำดับสำคัญมาก: กรอกฟอร์ม → กดสมัคร → ฟอร์มผ่าน validation → เปิดหน้ายินยอม PDPA → ยินยอม → ค่อยเรียก API สร้างบัญชี ถ้าผู้ใช้ปิดหน้ายินยอม จะไม่มีการเรียก API ใด ๆ เลย — ไม่มีบัญชีค้างในระบบ

ฟอร์มสมัคร

ฝั่ง backend บังคับแค่ phone/firstName/lastName แต่แอปตั้งใจบังคับครบทุกช่องเอง ส่วนที่อยู่ ข้อมูลสุขภาพ และผู้ติดต่อฉุกเฉิน ยกไปกรอกทีหลังในหน้าโปรไฟล์

  • เบอร์โทรศัพท์ — ตัวเลขล้วน 10 หลัก
  • ชื่อจริง / นามสกุล — สองช่องเรียงแถวเดียวกัน
  • ชื่อเล่น — บังคับ ("กรุณากรอกชื่อเล่น")
  • เพศ — dropdown ส่งค่าอังกฤษ male/female/other แสดงไทย ชาย/หญิง/อื่นๆ
  • วันเกิด — แตะเปิด date picker แสดงเป็น พ.ศ.
  • อีเมล — ตรวจรูปแบบด้วย regex

ด่านยินยอม PDPA

  • 1ดึงนโยบายจาก GET /pdpa — เนื้อหาเป็น HTML สำเร็จรูป แสดงด้วย flutter_html
  • 2ถ้า API ล่มหรือยังไม่มีเวอร์ชันเปิดใช้ (404) ใช้ฉบับที่ฝังมากับแอป bundled-2026-08-04 แทน — ไม่บล็อกการสมัคร
  • 3ต้องเลื่อนอ่านจนสุด checkbox จึงกดได้ ปุ่ม "ยินยอมและดำเนินการต่อ" จึงจะเปิด
  • 4กดปิด (X) = ยกเลิกการสมัคร กลับมาที่ฟอร์มโดยไม่เรียก API
  • 5ยินยอมแล้วบันทึกเวลา UTC + เวอร์ชันไว้ในเครื่อง แล้วส่ง pdpaConsent/pdpaConsentVersion ไปกับ register
ข้อควรรู้ ฝั่ง backend ยังไม่มีช่องรับความยินยอมนี้ — RegisterRequest ไม่มีฟิลด์ PDPA การบังคับยินยอมจึงอยู่ฝั่งแอปล้วน และยังไม่มี endpoint ให้อ่านสถานะย้อนหลัง
03

หน้าแรก — เรียงตามสิ่งที่ต้องรีบทำก่อน

/home

เข้าหน้านี้แล้วโหลดสองอย่างเรียงกัน: รายชื่อสมาชิกที่ดูแล แล้วตามด้วยรายการจองที่ยัง active ดึงลงเพื่อรีเฟรชได้ ถ้าโหลดไม่สำเร็จจะแทนที่ทั้งหน้าด้วยการ์ด "โหลดข้อมูลไม่สำเร็จ" + ปุ่มลองอีกครั้ง

ลำดับการ์ดไม่ตายตัว

บล็อก "การชำระเงิน" กับ "นัดหมายล่าสุด" สลับที่กันตามสถานการณ์ — ถ้ามีรายการรอชำระ บล็อกชำระเงินจะขึ้นก่อนเสมอ ถ้าไม่มีก็ลงไปอยู่ล่างในรูปแบบ empty state ("ไม่มีรายการค้างชำระ")

  • แถบตัวเลข 3 ช่อง — สมาชิก / นัดหมาย / รอชำระ อ่านจากข้อมูลจริงที่เพิ่งโหลด
  • บริการด่วน — 4 การ์ด แต่ละใบใช้สีหมวดของตัวเอง (Coral / Emerald / Amethyst / Rose) กดแล้วเข้าหน้าจอง
  • สมาชิกที่ดูแล — แถวอวาตาร์เลื่อนแนวนอน กดเข้าหน้าสมาชิก
  • กระดิ่งแจ้งเตือน — ยังไม่ทำงานจริง กดแล้วขึ้น snackbar บอกตรง ๆ ว่ายังไม่มีในโหมดจำลอง
04

สมาชิกที่ดูแล — ด่านบังคับก่อนจองได้

/members

การจองต้องระบุเสมอว่าจองให้ใคร บัญชีที่ยังไม่มีสมาชิกจึงเปิดหน้าจองไม่ได้เลย — หน้าจองจะกลายเป็นการ์ด "ยังไม่มีผู้รับบริการ" พร้อมปุ่มพากลับมาหน้านี้

  • 1กด "เพิ่มสมาชิก" (ปุ่มลอยมุมขวาล่าง) เปิด bottom sheet ฟอร์ม
  • 2กรอก ชื่อจริง / นามสกุล / ชื่อเล่น / ความสัมพันธ์ / เบอร์โทร / อายุ / เพศ / กรุ๊ปเลือด / หมายเหตุการดูแล
  • 3บันทึกแล้วรายชื่อรีเฟรชทันที ตั้งเป็นค่าเริ่มต้นได้หนึ่งคน
  • 4สมาชิกค่าเริ่มต้นจะถูกเลือกให้อัตโนมัติในขั้นจอง และที่อยู่ของเขากลายเป็นจุดรับตั้งต้น
  • ค้นหาได้จากชื่อ ความสัมพันธ์ หรือเบอร์โทร
  • ตัวกรอง 4 ชิป: ทั้งหมด / ตัวเอง / ครอบครัว / ค่าเริ่มต้น
  • เพดานจำนวน 5 คน (AppConfig.maxRelatives) แสดงบนแถบสรุปหัวหน้าจอ
ยังใช้ไม่ได้จริง ปุ่มลบสมาชิกจะได้ 404 — DELETE /user-relatives/{id} ยังไม่มีบน backend และการสร้างสมาชิกต้องยิง POST แล้วตาม PATCH ทันที เพราะ POST ไม่บันทึกชื่อเล่น/กรุ๊ปเลือด/วันเกิดให้
05

จองบริการ — wizard 5 ขั้นในหน้าเดียว

/booking

ทั้ง 5 ขั้นอยู่ใน PageView เดียว ปัดเองไม่ได้ — เดินหน้าได้เฉพาะปุ่ม "ถัดไป" เท่านั้น แถบล่างติดตรึงอยู่ตลอด แสดง ราคาโดยประมาณที่อัปเดตสดทุกครั้งที่เปลี่ยนบริการหรือช่วงเวลา

ขั้นชื่อขั้นผู้ใช้ทำอะไรด่านตรวจก่อนไปต่อ
1บริการเลือกการ์ดบริการจากแถวเลื่อนแนวนอนไม่มี (มีตัวเลือกแรกถูกเลือกไว้แล้ว)
2เวลาเลือกวันที่ + ช่วงเวลา (ชิปสำเร็จรูปหรือกำหนดเอง)เวลาสิ้นสุดต้องมากกว่าเวลาเริ่ม
3ผู้รับบริการเลือกสมาชิกหนึ่งคนต้องมีสมาชิกอย่างน้อย 1 คน
4สถานที่ปักจุดรับ (+ ปลายทางถ้าเป็นบริการรับ-ส่ง) และหมายเหตุต้องมีพิกัดจากแผนที่ ไม่ใช่พิมพ์ข้อความเปล่า
5ยืนยันตรวจสรุป แล้วกด "ยืนยันและไปชำระเงิน"ตรวจซ้ำทุกข้อ + ต้องหา PromptPay UUID เจอ
สูตรราคา ค่าบริการ = ค่าบริการต่อชั่วโมง × (นาทีที่ปัดขึ้นทีละ 30 นาที ÷ 60) แล้วบวกค่าธรรมเนียมแพลตฟอร์ม ฿20 — จองสองชั่วโมงกับบริการ ฿200/ชม. จึงได้ ฿420 พอดี ตัวเลขนี้เป็นเพียงค่าประมาณฝั่งแอป ยอดจริงมาจาก response ตอนสร้างการจอง
สองกับดักที่เคยทำให้จองไม่ผ่านทั้งระบบ 1) เวลาที่ส่งขึ้น backend ต้องเป็น RFC3339 พร้อม offset — toIso8601String() บน DateTime ท้องถิ่นไม่ใส่ timezone มาให้ Go จึงปฏิเสธทันที ใช้ _toRfc3339() เสมอ · 2) paymentMethodId ต้องเป็น UUID จริงจาก GET /payments/methods ไม่ใช่ slug — slug ของ PromptPay คือ qr_promptpay ใช้ไว้เทียบเท่านั้น
06

เลือกตำแหน่งบนแผนที่

LocationPickerPage — Navigator.push, ไม่มี route ของตัวเอง

วิดเจ็ตเดียวใช้ซ้ำทุกที่ที่ต้องปักหมุด: จุดรับและปลายทางในหน้าจอง และที่อยู่หลักในหน้าโปรไฟล์ ชื่อหน้าเปลี่ยนตามบริบท ("เลือกจุดรับ" / "เลือกจุดหมายปลายทาง" / "เลือกที่อยู่บนแผนที่")

  • 1ค้นหาด้วยชื่อสถานที่หรือที่อยู่ (geocoding ของระบบปฏิบัติการ ไม่ต้องใช้ API key)
  • 2หรือเลื่อนแผนที่เอง / กดปุ่มตำแหน่งปัจจุบัน (ขออนุญาต GPS)
  • 3ระบบแปลงพิกัดกลับเป็นข้อความที่อยู่ให้อัตโนมัติ ระหว่างรอขึ้น "กำลังค้นหาที่อยู่..."
  • 4กด "ยืนยันตำแหน่งนี้" ส่ง Address พร้อมพิกัดกลับไปให้หน้าที่เรียก
ทำไมต้องผ่านแผนที่ หน้าจองไม่ยอมให้ผ่านขั้นสถานที่ถ้ายังไม่มีพิกัด — พิมพ์ที่อยู่เป็นข้อความเปล่าอย่างเดียวไม่พอ เพราะระบบจับคู่ผู้ดูแลฝั่ง backend ใช้พิกัดคำนวณ ถ้าไม่ได้ปักจะขึ้น snackbar "กรุณาเลือกจุดรับบนแผนที่"

ข้อความเมื่อค้นหาไม่เจอ: “ไม่พบสถานที่ที่ค้นหา ลองระบุที่อยู่ให้ละเอียดขึ้น”

07

ชำระเงินด้วย PromptPay QR

/payment

หน้านี้หยิบรายการที่ค้างชำระของผู้ใช้ขึ้นมาเองเสมอ ไม่ต้องส่ง id เข้ามา ถ้าไม่มีรายการค้างจะขึ้นแค่ข้อความ "ไม่มีรายการที่รอชำระเงิน"

  • 1สรุปการจอง (บริการ / ผู้รับบริการ / เลขอ้างอิง / ยอดชำระ) บนการ์ดกระจกใบบน
  • 2QR สร้างขึ้น ในเครื่อง จากเลข PromptPay + ยอดเงิน ตามมาตรฐาน EMVCo ไม่ได้ขอจาก backend
  • 3นาฬิกาถอยหลังนับจาก expiredAt ของรายการชำระเงินจริง
  • 4ปุ่มยืนยันล็อกไว้ 5 วินาทีแรก ("กรุณาสแกน QR ก่อน") กันกดผ่านโดยไม่ได้จ่าย
  • 5กด "ฉันชำระเงินแล้ว" → ยิง confirm → เด้ง bottom sheet สำเร็จ → ไปหน้าติดตามสถานะ
ยังไม่ได้ทดสอบจริง QR ยังไม่เคยถูกสแกนด้วยแอปธนาคารจริง — ตรวจแค่อัลกอริทึม CRC16 กับ test vector ทางการเท่านั้น ถือเป็นความเสี่ยงที่ยังเปิดอยู่ก่อนขึ้น production
08

ติดตามสถานะ — ฝั่งแอปต้องถามเอง

/booking/status/:bookingId

ไม่มี push และไม่มี webhook การจับคู่ผู้ดูแลเกิดขึ้นแบบ async ฝั่ง backend แอปจึงต้องถาม GET /bookings/:id/mission ซ้ำ ๆ เอง จังหวะการถามปรับตามสถานะ

สถานะขณะนั้นถามซ้ำทุกเหตุผล
กำลังหาผู้ดูแล5 วินาทีช่วงที่สถานะเปลี่ยนได้ทุกวินาที ผู้ใช้จ้องจออยู่
จับคู่แล้ว20 วินาทีได้คนแล้ว เหลือรอความคืบหน้า ไม่ต้องถี่
กำลังดำเนินการ20 วินาทีอัปเดต checkpoint ระหว่างทำงาน
เสร็จสิ้น / ยกเลิก / หมดอายุหยุดถามสถานะปลายทาง ไม่เปลี่ยนอีก
คำเตือน 10 นาที ถ้าค้างที่ "กำลังหาผู้ดูแล" เกิน 10 นาที จะขึ้นแถบเตือนสีส้มให้ติดต่อฝ่ายบริการลูกค้า — ใส่ไว้ตรง ๆ เพราะ backend ยังมีช่องโหว่เรื่อง retry การจับคู่ที่รู้กันอยู่

ยกเลิกการจอง

/payment/booking/status/:bookingId

ยกเลิกได้สองที่ และข้อความอธิบายผลลัพธ์เปลี่ยนตามสถานะจริงของรายการ ไม่ได้ใช้ข้อความกลาง ๆ ใบเดียว

สถานะยกเลิกเองได้ข้อความที่ผู้ใช้เห็น
รอชำระเงินได้ยังไม่ได้ชำระเงิน ยกเลิกได้ทันที
กำลังหาผู้ดูแลได้จะหยุดการค้นหา และคืนเงินตามขั้นตอนของเจ้าหน้าที่
จับคู่แล้วได้ผู้ดูแลรับงานแล้ว ระบบจะแจ้งให้ทราบ และคืนเงินตามขั้นตอน
กำลังดำเนินการไม่ได้ต้องผ่านเจ้าหน้าที่ (พาร์ทเนอร์กำลังทำงานอยู่)
เสร็จสิ้น / ยกเลิกแล้ว / หมดอายุไม่ได้ปุ่มยกเลิกไม่ปรากฏ
  • ใส่เหตุผลได้แต่ไม่บังคับ จำกัด 500 ตัวอักษร
  • ถ้ารายการถูกยกเลิกไปแล้วก่อนหน้า ระบบไม่แจ้งเป็น error — ถือว่าได้ผลลัพธ์ที่ผู้ใช้ต้องการแล้ว แล้วรีเฟรชสถานะให้
  • ยกเลิกหลังจ่ายเงินแล้วจะขึ้นแถบส้ม "อยู่ระหว่างดำเนินการคืนเงิน เจ้าหน้าที่จะติดต่อกลับ"

โปรไฟล์ & เมนูย่อยทั้งหมด

/profile/profile/personal-information /profile/health-information/profile/addresses /profile/settings/booking/history

แท็บที่ 4 เป็นประตูเข้าเมนูย่อย 7 รายการ ทุกหน้าลูกเปิดเป็นเส้นทางเต็มจอ (ไม่มีแท็บล่าง) และมีปุ่มย้อนกลับของตัวเองที่พากลับ /profile เสมอ

เมนูคำอธิบายใต้ชื่อปลายทาง
ข้อมูลส่วนตัวชื่อ อีเมล วันเกิด และเพศ/profile/personal-information
ข้อมูลสุขภาพผู้ติดต่อฉุกเฉิน กรุ๊ปเลือด และประวัติการแพ้/profile/health-information

ตั้งค่าความปลอดภัยจัดการความปลอดภัยของบัญชี/profile/settings
